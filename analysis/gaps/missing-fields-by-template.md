# Missing / unmatched fields by template

Template-centric view of [`api-response-gaps.md`](./api-response-gaps.md) (which is field-centric — one row per field, listing templates). Same underlying data, grouped the other way: one row per template, listing every merge field whose `API Response available` was **No** or **Partial**, grouped by what kind of field it is.

**Groups:**
- **Static** — NOW-catalogue text/metadata (`orderName`, `nt.value(...)`, `nrt.value(...)`) — not hearing data at all; sourced from the `nows-metadata` reference-data catalogue.
- **Derived** — computed from the matched judicial result's own date (`amendmentdate`, `orderDate`).
- **Untraced** — the merge-field analysis found these are built by the legacy NowContent mapper layer from hearing/court-centre/offence data, but couldn't trace the exact source field-by-field (`label`, `value`, `es`, the Partial-status `amendmentDate` variant) — flagged honestly rather than guessed at.
- **Result-identifier lookups** — `dr.resultIdentifierExists(...)`/`resultPromptValue(...)` etc., keyed by a `judicialResultTypeId` UUID the API response has no stable equivalent for.
- **Prompt-based** — reachable only by fuzzy-matching a judicial result prompt's display label; no stable `promptReference` key in the API response.
- **Hearing/defendant/offence field** — a plain field on the hearing/case/defendant/offence that the API response's schema simply doesn't model yet (e.g. `defendant.pncId`, `orderingCourt.ljaCode`).
- **Court-application party detail** — applicant/respondent name/address/DOB — a party role the API response's `courtApplications` schema doesn't carry.
- **Recipient/addressee** — `orderAddressee.*` — out of scope for an eligibility/content API; this is a recipient-resolution concern owned elsewhere.
